# Дизайн: дашборд заказов Ozon FBS

## Цель

Создать личный дашборд для двух кабинетов Ozon, где можно видеть новые FBS-заказы, собранные отправления, подробности заказа и печатать этикетки. Дашборд и основная логика работают на сервере в Нидерландах; запросы к Seller API Ozon выполняются через локальный компьютер пользователя.

## Подходы

1. **Локальный агент — выбранный подход.** Агент на ПК сам устанавливает исходящее защищённое HTTPS-соединение с сервером, получает задания, вызывает Seller API и возвращает результат. Входящие порты на ПК не нужны; ключи API остаются локально.
2. **Сетевой туннель через ПК.** Серверный трафик целиком направляется через VPN или прокси на ПК. Это прозрачно для приложения, но требует постоянно поддерживать туннель и тщательнее ограничивать исходящий трафик.
3. **Вызовы из браузера.** Браузер обращается к Ozon напрямую. Такой вариант зависит от CORS и усложняет защиту ключей, поэтому для этого проекта не выбран.

Локальный агент выбран потому, что он оставляет бизнес-логику и хранение данных на сервере, а через локальную сеть выполняет только необходимые вызовы маркетплейса.

## Архитектура

- Один Git-репозиторий `fundvam-code/Books` содержит сервер, локальный агент, Docker-конфигурации и документацию.
- Серверная часть, PostgreSQL и обратный HTTPS-прокси запускаются на сервере через Docker Compose.
- Локальный агент запускается контейнером на ПК и сам опрашивает сервер через исходящее HTTPS-соединение. Он забирает задания синхронизации и печати этикеток.
- Сервер создаёт задания синхронизации раз в минуту и хранит их в PostgreSQL; отдельный брокер сообщений для первой версии не нужен.
- Поддерживаются два профиля Ozon, соответствующие двум наборам переменных `OZON_*_1` и `OZON_*_2` в существующем локальном `.env`.
- API-ключи Ozon доступны только локальному агенту. На сервер передаются данные заказов и временные PDF этикеток, но не ключи.

## Статусы и интерфейс

Ozon FBS использует `awaiting_packaging` для новых заказов, ожидающих упаковки, и `awaiting_deliver` для собранных отправлений, ожидающих отгрузки. В дашборде это будут колонки **«Ожидают сборки»** и **«Собраны — ждут отгрузки»**. Отдельного статуса «сейчас собирается» API не предоставляет.

В таблице и карточке заказа показываются номер и время заказа, срок отгрузки, товары, наименование и артикул/SKU, количество, цена, склад и способ доставки — только если эти поля возвращены API. Данные получателя не показываются в интерфейсе по умолчанию.

Для печати агент создаёт задание на генерацию этикеток средствами Seller API и забирает готовый PDF. PDF доступен через защищённый дашборд ограниченное время, после чего удаляется.

## Цели и границы

В первую версию входят:

- чтение заказов FBS из двух кабинетов;
- фильтрация по двум статусам выше;
- просмотр карточки заказа;
- получение и печать официальной PDF-этикетки Ozon;
- индикация доступности локального агента и ошибок API.

Не входят: другие маркетплейсы, изменение или подтверждение статусов заказа, отмена/отгрузка, аналитика продаж, управление товарами, автоматическая печать без действия пользователя.

## Защита и ограничения

- `.env` с ключами остаётся вне репозитория. В Git включается только пустой пример конфигурации.
- Для агента используется отдельный секрет соединения; секреты задаются локально и на сервере, не коммитятся.
- Публичный дашборд защищается HTTPS и базовой HTTP-аутентификацией (Basic Auth) на обратном прокси.
- Агенту нужны доступ к интернету и внешний IP, разрешённый Ozon. Если внешний IP компьютера меняется, может потребоваться обновить разрешение у маркетплейса.
- При отключённом ПК сервер показывает статус агента и возобновляет синхронизацию после восстановления соединения.
- PDF этикетки содержит данные отправления, хранится только временно и доступен только после входа в дашборд.

## Технический выбор для плана

Предлагаемый набор технологий: Python 3.12, FastAPI, PostgreSQL 16, SQLAlchemy 2, Jinja2 + HTMX, `httpx`, Docker Compose v2 и Caddy для HTTPS. В первой версии не используем отдельное SPA и Redis, чтобы уменьшить число сервисов.
